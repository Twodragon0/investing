# 커버리지 계획 (2026-08-27 재도출)

2026-08-27 세션에서 저커버리지 상위 4개 모듈이 모두 닫혔다(#1234·#1236·#1237·#1240).
그 결과 이전에 문서·가드에 적혀 있던 "다음 대상" 목록이 전부 낡았다. 이 문서는 **실측으로
재도출한 현재 목록**과 우선순위 기준, 그리고 각 단계에서 도달 가능한 게이트를 기록한다.

## 왜 목록을 문서에 박지 않는가

`tests/test_coverage_floor_guard.py` docstring 은 최대 저커버리지 모듈을 이름으로
나열하고 있었고, 이번에 그 값이 **실제로 틀렸다** — `generate_weekly_report` 를
"216 at 13%" 로 적어뒀는데 그 13% 는 다른 테스트가 import 만 해서 생긴 모듈 레벨
커버리지였고, 이 모듈만 대상으로 재면 **0%** 였다.

그래서 가드 docstring 에서는 목록을 걷어내고 재도출 명령만 남겼다(#1240). 이 문서는
그 재도출 결과를 **날짜와 함께** 남기는 스냅샷이다 — 낡으면 낡은 것으로 읽히도록
파일명에 날짜를 넣었다.

## 재도출 방법

```bash
python3 -m pytest tests/ -m "not i18n_e2e" --cov-report=term-missing --cov-fail-under=0
# → 출력에서 미커버 statement(3번째 열) 기준 내림차순 정렬
```

`%` 기준이 아니라 **미커버 statement 절대값** 기준으로 정렬한다. 게이트는 비율이
아니라 statement 수로 움직이므로(총계 24,778 중 몇 개가 미커버인가), 90% × 500줄
모듈이 30% × 100줄 모듈보다 게이트에 더 큰 영향을 준다.

### 이번 라운드는 성격이 다르다

직전 라운드(#1234·#1236·#1237·#1240)의 대상은 **테스트가 아예 없거나 게이팅 함수 하나만
덮인** 모듈이었다 — 0%·13%·17%·20%. 이번 상위 15개 중 테스트가 **0건인 것은
`enrich_existing_posts` 뿐이었고(그마저 삭제됨, 아래 절)**, 나머지는 3~89건을 이미
갖고 있다(비율 27~80%).

즉 이번은 **없는 테스트를 만드는 일이 아니라 있는 테스트를 깊게 하는 일**이다. 남은
미커버가 정상 경로가 아니라 **예외·폴백·조건 분기**에 몰려 있을 가능성이 높고, 그쪽은
"무엇이 조용히 틀리는가" 를 먼저 읽어야 해서 모듈당 설계 시간이 더 든다. 계획을 세울 때
직전 라운드의 속도를 그대로 가정하지 말 것.

## 우선순위 기준

이번 세션에서 쓴 기준을 그대로 이어간다 — **stmts 크기가 아니라 "실패해도 조용한 코드"**.
세 축을 곱해서 본다:

1. **미커버 크기** — 게이트를 실제로 움직이는가
2. **조용한 실패 위험** — 깨져도 워크플로우가 성공으로 끝나는가. 크론이 자동 실행하고
   아무도 즉시 읽지 않는 산출물(다이제스트·리포트)이 가장 위험하다
3. **격리 난이도** — 네트워크·디스크·시각 의존을 끊을 수 있는가

## 단계 배치와 게이트 전망

기준선은 **#1240·#1241 머지 + `enrich_existing_posts` 삭제 후** `20,799 / 24,645 = 84.39%`,
게이트 82. 규칙상 이미 **83** 까지 갈 수 있다(헤드룸 466 stmts) — T1 을 기다리지 않아도 된다.

각 단계는 해당 모듈을 ~98% 로 덮는다고 가정했다(잔여는 `__main__` 등 도달 불가 줄).
게이트는 매번 **462-stmts 규칙**("이미 수용한 가장 빡빡한 헤드룸 아래로는 래칫하지
않는다")을 만족하는 최댓값이다.

| 단계 | 모듈 | 회수 | 총계 전망 | 규칙상 최대 게이트 | 헤드룸 |
|---|---|---:|---:|---:|---:|
| **T1** | `generate_weekly_digest`, `collect_fmp_calendar`, `generate_ops_10am_digest` | 783 | 87.57% | **86** | 510 |
| **T2** | `collect_crypto_news`, `collect_social_media`, `collect_coinmarketcap` | 703 | 90.42% | **89** | 474 |
| **T3** | `improve_existing_posts`, `collect_market_indicators` | 426 | 92.15% | **90** | 653 |

전망치는 계획용이다 — 실제 게이트는 매 PR 에서 다시 실측해 결정한다. 이번 세션에서
81 이 **460 stmts** 로 462 기준에 2 부족해 거부된 사례가 있었고, 그건 전망으로는
잡히지 않는다.

### T1 을 먼저 하는 이유

세 모듈 모두 **크론이 만들고 아무도 즉시 읽지 않는 산출물**이다. `generate_weekly_report`
(#1240)와 같은 부류이고, 거기서 실제로 잡아낸 위험이 그대로 적용된다 — 주 경계 계산,
파싱 정규식, 중복 가드. `collect_fmp_calendar` 는 27% 로 비율도 가장 낮다.

`collect_crypto_news`(288 미커버)를 T2 로 미룬 이유는 이미 24건의 테스트가 있어
**남은 미커버가 예외·폴백 경로에 몰려 있을 가능성**이 높고, 그쪽은 T1 보다 설계 시간이
더 든다.

## 해소됨 — `enrich_existing_posts.py` 삭제 (조사 후)

이 문서 초안은 "확인 필요, 죽은 코드로 단정하지 않는다" 로 남겨뒀다. 조사 결과 **정규식이
렌더러 변경을 따라가지 못해 5개월간 조용한 no-op** 이었음이 드러나 삭제했다.

| 확인 항목 | 실측 |
|---|---|
| 호출처 | 워크플로우·코드 0건. `README.md` / `scripts/AGENTS.md` 트리 주석만 |
| 최종 수정 | 2026-03-07 (약 6개월 전) |
| 대상 마크업 생존 | **살아 있다** — `common/themed_news_renderer.py` 가 지금도 생성, 월 54~62 포스트 |
| 스크립트가 매칭 가능한 카드 | **5,234개 중 357개(6.8%), 2026-04 이후 0개** |
| 남은 실제 작업량 | 2026-06~08 카드 2,634개 중 설명 누락 **46개(1.7%)** |

원인은 마크업 드리프트다. 렌더러가 2026-04 부터 `<div class="news-card-item news-sev-{severity}">`
를 내는데 스크립트의 `_CARD_RE` 는 `class="news-card-item"` **정확 일치**였다. 그래서 실행하면
"0건 처리" 로 **성공처럼 끝난다** — 정확히 이 저장소가 경계하는 "실패해도 조용한 코드" 다.

삭제를 고른 이유: 5개월간 아무도 못 쓴 것을 눈치채지 못했고(= 수요가 없다), 정규식을 고쳐
되살려도 얻는 것은 카드 46개 보완이다. 133 stmts 가 분모에서 빠져 총계도 오른다(0% 였으므로
#1241 과 달리 삭제가 커버리지에도 이득이다). 재필요 시 git 히스토리에서 되살릴 수 있다.

**교훈**: 마크업을 정규식으로 잡는 백필 스크립트는 렌더러와 함께 움직이지 않으면 조용히
죽는다. 새로 쓰는 백필 도구는 렌더러가 내는 마크업을 **테스트로 묶어** 드리프트를 red 로
드러내야 한다.

## 작업 시 반드시 적용할 격리 규칙

2026-08-27 세션에서 **실제로 사고가 났던** 항목들이다. 새 커버리지 PR 은 이 세 가지를
먼저 확인한다.

| 함정 | 실제 사고 | 대응 |
|---|---|---|
| **트리 오염** | `collect_geopolitical` 테스트가 실제 이미지 생성기를 호출해 `assets/images/generated/*.{png,webp,avif}` 3파일 수정 (#1236) | 이미지 생성 함수를 fixture 로 기본 차단. 스위트 후 `git status` 확인 |
| **conftest 네트워크 차단의 사각지대** | 차단은 `requests` 의 `HTTPAdapter.send` 만 막는다. `urllib` 을 직접 쓰는 모듈은 통과하고, `os.getenv` 로 실제 토큰을 집으면 외부로 나간다 (#1237) | 모듈 네임스페이스의 fetch 함수를 대체 + 관련 env 삭제 + `urlopen` 실패 스텁 |
| **프로덕션 경로 상수** | `POSTS_DIR` / `DOCS_DIR` / `REPO_ROOT` 는 임포트 시점에 `__file__` 로부터 계산된다. 격리 없이 `main()` 을 돌리면 실제 산출물을 쓴다 | 상수를 임포트하지 않고 `monkeypatch.setattr` 로 tmp 주입 |

추가로, **관측 지점을 최종 산출물이 아니라 함수 출력으로** 잡아야 하는 경우가 있다 —
`post_generator` 가 generic-description 정책으로 값을 갈아치우므로 포스트 파일만 보면
`run()` 의 분기 동작을 확인할 수 없다(#1236). `create_post` 인자를 캡처하는 편이 정확하다.
