# 수집기 푸시 배칭 설계

> 작성 2026-08-08. 배경 실측은 `branch-protection.md` 의 "Vercel 배포 트리거" 절.

## 문제

2026-08-08 실측에서 **main 커밋 1건 = Vercel Production 배포 레코드 1건**이 SHA
기준 1:1(26 ↔ 26, 중복 0)로 확인됐다. `ignoreCommand` 는 빌드 시간만 줄이고
레코드는 그대로 만든다. 따라서 배포 레코드를 줄이는 레버는 **main 커밋 수 자체**
하나뿐이고, 그중 자동화가 만드는 몫이 수집기 푸시다.

## 실측 — 무엇이 main 커밋을 만드는가

2026-08-07(관측 기간 중 최다, 61건) 분해:

| 출처 | 건수 |
|---|---|
| 수집기 (`chore: collect *`) | 28 |
| PR 머지 (`(#NNNN)`) | 25 |
| 머지 커밋 | 3 |
| 기타 자동화(백필·품질 보정) | 5 |

일자별 main 커밋: 08-04 40 / 08-05 39 / 08-06 47 / 08-07 61.

**PR 머지 25건은 그날의 개발 활동 스파이크이지 정상 부하가 아니다.** 정상 부하의
자동화 몫은 수집기 28 + 기타 5 ≈ 33건/일이다.

수집기는 13개, 스케줄 실행은 약 40회/일 → 커밋 28건. 즉 실행의 약 70%가 커밋을
만든다(나머지는 `No new posts to commit`).

### 수집기 커밋 321건 분류 (최근 400커밋 스캔)

| 분류 | 건수 | 비율 | 빌드 | 레코드 |
|---|---|---|---|---|
| 콘텐츠 있음 (`_posts`/`assets` 포함) | 148 | 46.1% | 함 | 생성 |
| `_state`-only, **metrics/cache 뿐** | 132 | **41.1%** | skip | 생성 |
| `_state`-only, **dedup(`*_seen.json`) 포함** | 41 | 12.8% | skip | 생성 |

두 번째 줄이 핵심이다. 이 커밋들이 바꾸는 것은 딱 두 가지다:

- `_state/image_rejection_metrics.json` — `last_seen` 타임스탬프 한 줄
- `_state/translation_cache.json` — 번역 결과 캐시 증분

사이트 산출물에 아무 영향이 없고, 빌드도 이미 skip 되며, **배포 레코드만 만든다.**

## 옵션

### A. `_state`-only 커밋 중 metrics/cache 뿐인 것은 커밋하지 않는다

- **절감**: 수집기 커밋의 41.1% (28/일 → 약 16.5/일). 콘텐츠 지연 **0**.
- **비용**: 그 실행에서 늘어난 번역 캐시가 유실돼 다음 실행이 재번역한다. 콘텐츠
  커밋이 46%의 비율로 계속 나므로 캐시가 영구히 비는 것은 아니다.
- **부작용**: `generate_weekly_report.py:266` 이 `last_seen` 을 리포트의 "기간"
  표시에 쓴다. 종료 시각이 최대 한 배치만큼 옛날 값으로 보인다 — 표시 전용이고
  다른 소비자는 없다.
- **하면 안 되는 것**: `*_seen.json` 이 섞인 12.8% 까지 함께 버리는 것. 이건
  dedup 상태다. 버려도 되는지는 "재평가가 결정적인가"에 달려 있고 확인되지
  않았다. 이 옵션은 **파일 화이트리스트로만** 판정한다(알려진 안전 파일 집합에
  포함될 때만 skip, 그 외에는 오늘과 동일하게 커밋).

### B. `_state` 를 main 밖 전용 브랜치로 분리

- **절감**: `_state`-only 커밋 53.9%가 main 에서 완전히 사라진다. 콘텐츠 커밋의
  diff 도 작아지고, `ignoreCommand` 의 `_state` 제외와 `.gitattributes` 의
  `merge=ours` 드라이버, 그리고 python-collect 액션의 충돌 재시도 로직 상당수가
  불필요해진다.
- **비용**: 13개 수집기 전부가 상태 브랜치를 fetch/push 하도록 수정. 상태 브랜치
  자체도 프리뷰 레코드를 만든다(끄려면 그 브랜치의 `vercel.json` 이 필요하다 —
  `branch-protection.md` 의 후속 실측 참조).
- **위험**: 포스트 커밋과 상태 푸시의 **원자성 상실**. 포스트는 main 에 올라갔는데
  상태 푸시가 실패하면 다음 실행이 같은 항목을 다시 발행한다. 현재 구조는 둘이 한
  커밋이라 이 실패 모드가 없다.

### C. 시간창 배칭 — 13개 수집기를 3~4개 워크플로우로 통합

- **절감**: 수집기 커밋 28/일 → 3~4/일. 최대치.
- **비용**: 콘텐츠 발행이 최대 창 길이만큼 지연된다. 현재 크론은 시장 시간에
  맞춰 의도적으로 배치돼 있다(KR 개장 07:15, US 프리마켓 15:15, US 개장 21:15
  등) — 통합하면 그 의도가 깨진다.
- **위험**: 실패 격리 상실. 한 수집기의 실패가 배치 전체의 커밋에 영향을 준다.

## 권장

**A 를 먼저 한다.** 콘텐츠 지연이 0이고, 변경 지점이 `python-collect` 액션의
"Commit and push" 스텝 한 곳이며, 되돌리기 쉽다. 41% 절감이 부족하다고 판명되면
그때 B 또는 C 를 검토한다 — 둘 다 A 와 배타적이지 않다.

C 는 마지막에 둔다. 이 사이트의 상품은 뉴스의 신선도이고, 배포 레코드를 아끼려고
발행을 늦추는 것은 목적과 수단이 뒤집힌 거래다.

### A 의 구현 스케치

`.github/actions/python-collect/action.yml` 의 "Commit and push" 스텝에서
`git add` 이후 `git diff --staged --quiet` 판정 **전에**:

1. staged 경로 집합을 구한다 (`git diff --staged --name-only`).
2. 그 집합이 화이트리스트의 부분집합이면 `git reset` 하고 "no-op state churn,
   skipping commit" 을 로그로 남긴 뒤 종료한다.
3. 화이트리스트는 액션 입력이 아니라 **액션 안에 상수로** 둔다. 수집기별로 다르게
   줄 수 있게 하면 어느 수집기가 dedup 상태를 흘리는지 추적이 불가능해진다.

초기 화이트리스트(실측 기반, 이 둘만):

```
_state/image_rejection_metrics.json
_state/translation_cache.json
```

### A 를 머지하기 전에 통과해야 하는 게이트

- [ ] 가드 테스트: 화이트리스트에 `*_seen.json` 패턴이 들어오면 red. 방향은
      presence(금지 패턴 부재). `docs/devsecops/ci-regression-guards.md` 규약을 따를 것.
- [ ] non-vacuous 증명: 화이트리스트에 `_state/crypto_news_seen.json` 을 넣은
      임시 사본에서 가드가 실제로 FAIL 하는지.
- [ ] 수집기 1개(예: `collect-blockchain`, 1회/일이라 관측이 쉽다)에 먼저 적용해
      최소 3일 관측 후 나머지로 확대.
- [ ] 관측 지표: 해당 수집기의 커밋 수 감소, 그리고 **중복 포스트 0건**.

## 남는 불확실성

**레코드를 줄이면 쿼터가 실제로 덜 소진되는지는 확인되지 않았다.** 2026-08-07 의
거절 25건은 하루 총량이 아니라 15:54–17:56 이라는 **시간 구간**에 12건 연속으로
몰렸다. 분당/시간당 생성률에 반응하는 제한이라면, 하루 총 레코드를 41% 줄여도
피크 구간이 그대로면 거절은 그대로일 수 있다. A 를 적용한 뒤 거절 건수를 같은
방식(`vercel ls` 전체 페이지네이션 + 무 레코드 커밋 대조)으로 재측정해서 이
가정을 검증할 것.
