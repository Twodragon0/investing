# 수집기 푸시 배칭 설계

> 작성 2026-08-08. 배경 실측은 `branch-protection.md` 의 "Vercel 배포 트리거" 절.

## 문제

2026-08-08 실측에서 **main 커밋 1건 = Vercel Production 배포 레코드 1건**이 SHA
기준 1:1(26 ↔ 26, 중복 0)로 확인됐다. `ignoreCommand` 는 빌드 시간만 줄이고
레코드는 그대로 만든다. 따라서 배포 레코드를 줄이는 레버는 **main 커밋 수 자체**
하나뿐이고, 그중 자동화가 만드는 몫이 수집기 푸시다.

## 실측 — 무엇이 main 커밋을 만드는가

2026-08-07(관측 기간 중 최다, 61건) 분해:

| 출처 | 건수 |
|---|---|
| 수집기 (`chore: collect *`) | 28 |
| PR 머지 (`(#NNNN)`) | 25 |
| 머지 커밋 | 3 |
| 기타 자동화(백필·품질 보정) | 5 |

일자별 main 커밋: 08-04 40 / 08-05 39 / 08-06 47 / 08-07 61.

**PR 머지 25건은 그날의 개발 활동 스파이크이지 정상 부하가 아니다.** 정상 부하의
자동화 몫은 수집기 28 + 기타 5 ≈ 33건/일이다.

수집기는 13개, 스케줄 실행은 약 40회/일 → 커밋 28건. 즉 실행의 약 70%가 커밋을
만든다(나머지는 `No new posts to commit`).

### 수집기 커밋 321건 분류 (최근 400커밋 스캔)

| 분류 | 건수 | 비율 | 빌드 | 레코드 |
|---|---|---|---|---|
| 콘텐츠 있음 (`_posts`/`assets` 포함) | 148 | 46.1% | 함 | 생성 |
| `_state`-only, **metrics/cache 뿐** | 132 | **41.1%** | skip | 생성 |
| `_state`-only, **dedup(`*_seen.json`) 포함** | 41 | 12.8% | skip | 생성 |

두 번째 줄이 핵심이다. 이 커밋들이 바꾸는 것은 딱 두 가지다:

- `_state/image_rejection_metrics.json` — `last_seen` 타임스탬프 한 줄
- `_state/translation_cache.json` — 번역 결과 캐시 증분

사이트 산출물에 아무 영향이 없고, 빌드도 이미 skip 되며, **배포 레코드만 만든다.**

## 옵션

### A. `_state`-only 커밋 중 metrics/cache 뿐인 것은 커밋하지 않는다

- **절감**: 수집기 커밋의 41.1% (28/일 → 약 16.5/일). 콘텐츠 지연 **0**.
- **비용**: 그 실행에서 늘어난 번역 캐시가 유실돼 다음 실행이 재번역한다. 콘텐츠
  커밋이 46%의 비율로 계속 나므로 캐시가 영구히 비는 것은 아니다.
- **부작용**: `generate_weekly_report.py:266` 이 `last_seen` 을 리포트의 "기간"
  표시에 쓴다. 종료 시각이 최대 한 배치만큼 옛날 값으로 보인다 — 표시 전용이고
  다른 소비자는 없다.
- **하면 안 되는 것**: `*_seen.json` 이 섞인 12.8% 까지 함께 버리는 것. 이건
  dedup 상태다. 버려도 되는지는 "재평가가 결정적인가"에 달려 있고 확인되지
  않았다. 이 옵션은 **파일 화이트리스트로만** 판정한다(알려진 안전 파일 집합에
  포함될 때만 skip, 그 외에는 오늘과 동일하게 커밋).

### B. `_state` 를 main 밖 전용 브랜치로 분리

- **절감**: `_state`-only 커밋 53.9%가 main 에서 완전히 사라진다. 콘텐츠 커밋의
  diff 도 작아지고, `ignoreCommand` 의 `_state` 제외와 `.gitattributes` 의
  `merge=ours` 드라이버, 그리고 python-collect 액션의 충돌 재시도 로직 상당수가
  불필요해진다.
- **비용**: 13개 수집기 전부가 상태 브랜치를 fetch/push 하도록 수정. 상태 브랜치
  자체도 프리뷰 레코드를 만든다(끄려면 그 브랜치의 `vercel.json` 이 필요하다 —
  `branch-protection.md` 의 후속 실측 참조).
- **위험**: 포스트 커밋과 상태 푸시의 **원자성 상실**. 포스트는 main 에 올라갔는데
  상태 푸시가 실패하면 다음 실행이 같은 항목을 다시 발행한다. 현재 구조는 둘이 한
  커밋이라 이 실패 모드가 없다.

### C. 시간창 배칭 — 13개 수집기를 3~4개 워크플로우로 통합

- **절감**: 수집기 커밋 28/일 → 3~4/일. 최대치.
- **비용**: 콘텐츠 발행이 최대 창 길이만큼 지연된다. 현재 크론은 시장 시간에
  맞춰 의도적으로 배치돼 있다(KR 개장 07:15, US 프리마켓 15:15, US 개장 21:15
  등) — 통합하면 그 의도가 깨진다.
- **위험**: 실패 격리 상실. 한 수집기의 실패가 배치 전체의 커밋에 영향을 준다.

## 권장

**A 를 먼저 한다.** 콘텐츠 지연이 0이고, 변경 지점이 `python-collect` 액션의
"Commit and push" 스텝 한 곳이며, 되돌리기 쉽다. 41% 절감이 부족하다고 판명되면
그때 B 또는 C 를 검토한다 — 둘 다 A 와 배타적이지 않다.

C 는 마지막에 둔다. 이 사이트의 상품은 뉴스의 신선도이고, 배포 레코드를 아끼려고
발행을 늦추는 것은 목적과 수단이 뒤집힌 거래다.

### A 의 구현 스케치

`.github/actions/python-collect/action.yml` 의 "Commit and push" 스텝에서
`git add` 이후 `git diff --staged --quiet` 판정 **전에**:

1. staged 경로 집합을 구한다 (`git diff --staged --name-only`).
2. 그 집합이 화이트리스트의 부분집합이면 `git reset` 하고 "no-op state churn,
   skipping commit" 을 로그로 남긴 뒤 종료한다.
3. 화이트리스트는 액션 입력이 아니라 **액션 안에 상수로** 둔다. 수집기별로 다르게
   줄 수 있게 하면 어느 수집기가 dedup 상태를 흘리는지 추적이 불가능해진다.

초기 화이트리스트(실측 기반, 이 둘만):

```
_state/image_rejection_metrics.json
_state/translation_cache.json
```

### 관측 지표의 좁힌 정의 (2026-08-10)

"중복 포스트 0건" 을 그대로 측정하려 했을 때 **베이스라인이 이미 실패로 보였다.**
파일럿 전 regulatory 포스트 8개에서 항목 URL 32건이 여러 날 재등장했다. 원인을
따라가 보니 파일럿과 무관한 설계된 동작이었다:

- 수집기는 실행 안에서 `deduplicate_by_url` 로 중복을 걷고, 포스트 수준에서
  `mark_seen(post_title, "consolidated")` 로 재발행을 막는다.
- 그러나 **지난 날 포스트에 실린 항목을 오늘 피드에서 배제하지는 않는다.** 일일
  리포트는 그 시점 피드(피드당 `limit=10`)의 스냅샷이라, 아직 목록에 남아 있는
  FSC 공지는 매일 다시 실린다.

따라서 게이트는 **포스트 수준 중복**으로만 잡는다:

| 검사 | 게이트 | 근거 |
|---|---|---|
| 같은 `title` 을 가진 포스트 파일 2개 이상 | ✓ | `mark_seen(post_title, …)` 계약의 직접 위반 |
| 같은 (날짜, 종류) 슬롯에 파일 2개 이상 (`…-report-2.md`) | ✓ | 제목 없는 포스트를 잡는 유일한 경로 |
| 항목 URL 재등장 | ✗ 참고용 | 위 스냅샷 구조상 정상. 게이트로 쓰면 무죄인 파일럿이 실패로 읽힌다 |

슬롯 검사는 `kind` 의 꼬리 숫자를 떼고 묶는다. 파일명을 그대로 키로 쓰면 두 파일이
같은 키를 가질 수 없어(파일시스템이 막는다) **검사가 구조적으로 도달 불가**가 된다 —
초안이 실제로 그랬고 non-vacuous 증명에서 걸렸다.

### 절감 지표의 부하 보정 (2026-08-11)

"수집기 커밋 수 감소" 를 **원값**으로 읽으면 절감의 증거가 되지 못한다. 커밋 수는
그날 수집기가 몇 번 돌았는지, 뉴스가 얼마나 나왔는지에 따라 파일럿과 무관하게
움직인다. 파일럿 전후를 원값으로 비교하면 그 변동이 절감으로 위장한다.

`check_pilot_observation.py` 의 `[4]` 절이 두 비율을 나란히 출력한다. 교란원이 서로
달라 한쪽이 놓치는 것을 다른 쪽이 잡는다:

| 지표 | 분모 | 상쇄하는 교란 | 데이터 원천 |
|---|---|---|---|
| 실행당 커밋 | 워크플로우 실행 수 | "몇 번 돌았나" | `gh run list` (없으면 graceful skip) |
| 대조군 비 | 파일럿 미적용 수집기의 커밋 수 | 뉴스량 등 전 수집기 공통 변동 | `git log` (항상 동작) |

**`main` 총 커밋 수는 분모로 쓰지 않는다.** 위 "실측" 절이 보여주듯 그 값은 PR
머지에 지배된다(08-07 은 61건 중 25건). 개발이 활발한 날 regulatory 비중이
파일럿과 무관하게 떨어져 절감으로 오독된다.

전·후 구간의 길이가 달라도 된다 — 둘 다 비율이라 기간에 정규화돼 있다. 대신 두
계열에 **같은 창**을 강제해야 한다. 커밋은 git `--since` 로, 실행은 gh `--limit`
으로 각각 잘려 오므로 그대로 두면 창이 어긋난다.

**어긋남의 방향은 둘 다 있고, 위험한 쪽은 절단이다** (2026-08-12 리뷰에서 정정):

- 실행이 창보다 **멀리** 오면 pre_den 이 부풀어 전 구간 비율이 내려가고 post/pre 가
  커진다 → 절감 **과소**평가. `build_ratio` 의 `since` 가 이걸 막는다.
- 실행 예산(`--limit`)이 모자라면 gh 가 **최신순**으로 주므로 잘려 나가는 것은 전
  구간이다. pre_den 이 줄어 전 구간 비율이 올라가고 post/pre 가 작아진다 → 절감
  **과대**평가. `since` 는 이걸 못 막는다 — gh 가 애초에 안 준 실행은 만들어낼 수 없다.

초안의 `max(30, days * 6)` 은 crypto 실측 실행률(5.86회/일)과 사실상 같아 마진이
구조적으로 0이었다. 7일 창에서 예산 42, 창 내 실행 41 — 여유 1건이었다. `run_budget()`
을 `max(60, days * 12)` 로 올리고, 받아온 가장 오래된 실행이 창 시작보다 뒤면 경고한다.

한계 두 가지:

- **경계 귀속** — 커밋은 커밋 시각, 실행은 실행 시작 시각으로 나눈다. 머지 직전에
  시작해 직후에 커밋한 실행은 분자와 분모가 갈릴 수 있다(최대 1실행). 후 구간
  표본이 한 자릿수일 때 무시할 수 없어 분자/분모 **원값을 함께 출력**한다.
- **대조군 오염** — 파일럿을 확대하면 그 수집기를 `CONTROL_COLLECTORS` 에서 빼야
  한다. 안 빼면 분모도 함께 줄어 절감이 과소평가된다.

절감은 **게이트가 아니다.** 스크립트의 종료 코드는 여전히 포스트 수준 중복만 본다.
관측 기간이 3일(설계 게이트)에 못 미치면 숫자를 내되 "판정 보류" 로 경고한다.

2026-08-11 시점 실측 (관측 1.3일 — 판정 보류, 방향 참고용):

```
실행당 커밋   전 1.00 (17/17)  후 0.75 (3/4)   → -25.0%
대조군 비     전 0.159 (17/107) 후 0.130 (3/23) → -17.9%
```

두 지표가 갈리는 것 자체가 표본이 작다는 신호다. 아래 "판정 기준" 절 참조.

### 판정 기준을 절감 %에서 포착률로 (2026-08-11)

**절감 %는 이 파일럿의 표본으로 판정할 수 없다.** skip 비율의 95% Wilson 신뢰구간:

| 표본 | CI 폭 |
|---|---|
| 08-13 게이트 (9실행) | 0.53 — 51.9%와 25%를 구분 못 함 |
| regulatory 단독 30일 (90실행) | 0.20 |
| 6개 확대 3일 (68실행) | 0.22 |

해상도는 √n 으로만 늘어난다. 실측 실행률(crypto 6.0 / stock 5.1 / social 4.1 /
political 2.1 / geopolitical 2.1 / regulatory 3.0 = **22.4회/일**)을 보면, regulatory
단독 30일이 주는 해상도(폭 0.20, 90실행)를 확대로 얻으려면 90/22.4 ≈ **4.0일**이다.
**관측 연장은 확대보다 7.5배 비효율적이다.**

> 정정 (2026-08-12 리뷰): 합이 22.6 이 아니라 22.4 다. 그리고 "3일" 과 "10배" 도
> 틀렸다 — 3일 확대는 67실행으로 폭 0.22 이지 0.20 이 아니다. 위 CI 폭 값들은 각각
> 다른 p 를 함의해 어떤 단일 p 로도 재현되지 않는다(문서 자신의 벤치마크 p=0.519 로
> 계산하면 0.547 / 0.202 / 0.231). 결론의 방향은 그대로다.

대신 **사건의 유무**를 묻는 두 지표는 표본이 작아도 판정된다 (`[5]` 절):

| 지표 | 질문 | 원천 |
|---|---|---|
| 누출 | 파일럿 후에도 화이트리스트 부분집합 커밋이 남아 있는가 | git |
| 오검출 | skip 이 화이트리스트 밖까지 버렸는가 | gh 로그 (`--with-runs`) |

둘 다 "0이어야 한다" 는 단언이라 n=4 로도 반증 가능하다.

화이트리스트는 액션(`NOOP_STATE_PATHS`)에서 읽는다. 스크립트에 복사하면 액션이 바뀔
때 조용히 어긋나고, 어긋난 화이트리스트는 판정을 거짓 PASS 로 만든다. 읽기 실패 시
빈 집합으로 폴백하지 않고 **판정을 보류**한다 — 빈 집합이면 모든 `_state`-only

위 "식별 한계" 는 24h/95 · 30h/106 · 36h/116 이 모두 비슷하게 들어맞아 창 폭과 임계가

였다. 세 창 전부로 집계해 보니 **답은 '아무것도'** 다.

#### 롤링 피크는 파일럿이 아니라 개발 활동이 만든다 (2026-08-14 실측)

위 논지는 "파일럿의 기여가 작다" 였는데, 그것만으로는 **피크가 내려갔을 때 파일럿
공으로 읽는 오독**을 막지 못한다. `branch-protection.md` 의 "재측정 (2026-08-10)"
절차를 그대로 돌려 피크 창의 구성을 실측했다 — `vercel ls` 를 `--next` 로
페이지네이션 → `git log origin/main` 과 SHA 대조 → 90초 이내 후속 커밋이 레코드를
받았으면 non-head 로 분리. 손으로 돌리던 절차는 `scripts/tools/check_vercel_quota.py`
로 고정했다:

```

  --pilot-merged 2026-08-10T13:14:51+09:00
# 수집 538건 (production 425 / preview 113), main 커밋 453건
```

먼저 절차가 재현되는지부터 확인한다. 거절 집계가 08-10 재측정과 일치한다:

| 거절 | **24** | 24 |
| 일자별 거절 | 08-05 1 / 08-07 22 / 08-09 1 | 동일 |

거절 24건은 전부 파일럿 전이고, 파일럿 후 138커밋은 1건(non-head)을 빼고 모두
레코드를 받았다.

롤링 최대를 그냥 보면 08-10·08-11 이 59로 가장 큰데, 그 창들은 파일럿 전 레코드를

일자별 24h 피크(창 귀속 무시, 전 레코드): 08-04 51 / 08-05 55 / 08-06 71 /
**08-07 95** / 08-08 86 / 08-09 45 / 08-10 59 / 08-11 59 / 08-12 52 / 08-13 45.

**피크는 95 → 52 로 떨어졌지만 파일럿 효과가 아니다.** 두 피크 창의 레코드 구성이
방향을 뒤집는다:

| 창 | 총 | 수집기 | PR 머지 | 그 외 | preview(PR) | 개발 활동 소계 |
|---|---|---|---|---|---|---|
| 08-07 12:30 (전) | 95 | 30 (32%) | 16 | 6 | 43 | **65 (68%)** |
| 08-12 18:44 (후) | 52 | **36 (69%)** | 4 | 1 | 11 | 16 (31%) |

수집기 레코드는 30 → **36 으로 오히려 늘었다.** 피크가 43건 빠진 것은 전적으로 개발
활동이 줄어서다 — preview 43→11, PR 머지 16→4. 지배 항이 파일럿이 건드리지 않는
축에 있다.

**철회 — "08-07 의 30 은 포화로 검열된 값이다".** 초안은 그날 거절이 수집기 레코드를
억눌렀으니 30을 보정해서 읽어야 한다고 적었는데, 세 군데가 틀렸다(2026-08-14 리뷰):
그날 거절은 24건이 아니라 **22건**이고(24는 전 기간 총계), 그중 수집기/자동은 11이
아니라 **9건**이며(11도 전 기간 기준), 무엇보다 **피크 창 안의 거절은 0건**이다 —
창은 08-06 12:30:26 ~ 08-07 12:30:26 인데 그날 첫 거절은 **12:48:19**로 창이 닫히고
18분 뒤다. 검열은 일어나지 않았다. 따라서 30 은 보정 없이 그대로 읽는 값이고,
"피크 하락 = 파일럿" 부정 논거는 보정 논의 자체가 필요 없다.

**"파일럿 후 거절 0건" 도 성공의 증거가 아니다.** 파일럿 후 138커밋 중 137건이
레코드를 받았고 거절은 0인데, 파일럿 **전**에도 08-04·08-06·08-08·08-10 은 거절
0건이었다. 포화 사건은 전 기간 1회(08-07)뿐이라 0/1 계열이고, 위 "검정력 한계"

#### 정정 (2026-08-12 리뷰) — 대조군을 좁힌 것이 틀렸다

위 판단의 원래 근거는 "나머지 7개는 no-op 0건이라 파일럿에 반응할 수 없는 상수 항이니
대조군에 넣으면 분모만 키워 민감도를 떨어뜨린다" 였다. **DiD 에서 이 논리는 뒤집혀
있다.** 대조군의 요건은 두 가지다:

1. 파일럿에 반응하지 않을 것 (오염 0)
2. 공통 교란(뉴스량)을 탈 것

no-op 0건인 수집기는 1번을 **완벽히** 만족하고, 콘텐츠 커밋으로 뉴스량에 반응하므로
2번도 만족한다. 배제할 이유가 아니라 자격 요건이었다.

실측이 그대로 보여준다 (최근 7일, regulatory 파일럿 기준):

| 대조군 | 전 | 후 | 델타 | SE(log RR) |
|---|---|---|---|---|
| 2개 (초안) | 0.700 (14/20) | 0.625 (5/8) | -10.7% | **0.668** |
| 5개 (그 이전) | 0.159 (14/88) | 0.122 (5/41) | -23.3% | 0.554 |
| **9개 (채택)** | 0.200 (14/70) | 0.156 (5/32) | -21.9% | **0.563** |

좁힌 쪽이 SE 가 19% 크고, 추정치도 다른 두 대조군과 갈린다. `CONTROL_COLLECTORS` 를
**비-파일럿 수집기 전부**로 되돌렸다. 부수 효과로 2차 확대(political·geopolitical)를
해도 대조군 비가 살아남는다 — 아래 "2차 확대" 문단의 전제가 사라졌다.

**철회 — "대조군 교체가 추정치를 바꾸지 않는다".** 이 절에는 5개(-33.7%)와
2개(-33.3%)가 0.4%p 안에서 일치하므로 절감 추정이 대조군 선택에 좌우되지 않는다고
적혀 있었다. **근거가 무효다.** 두 델타는 분자(파일럿 15/4)를 공유하고 오직 대조군
post/pre 비 하나에서만 갈리는 구조라, 두 번의 독립 확인이 아니라 한 숫자의 우연이다
(37/92 = 0.402 vs 8/20 = 0.400). 실제로 7시간 뒤 같은 도구로 재측정하니 -23.3% 와
-10.7% 로 **12.6%p 갈렸다.** 커밋 한 건이 경계를 넘고 한 건이 추가된 것만으로 2개
대조군 추정치가 22.6%p 움직였다.

**스캔 창 함정은 그대로 유효하다.** 3000커밋으로 넓히면 defi llama 121건(63.0%) ·
defi yields 105건(51.5%) 의 no-op 이 잡히는데 **전부 2026-07-13 이전**이고 그 뒤로는
0건이다. 그 수치를 "지금도 no-op 을 만드는 수집기" 의 근거로 읽으면 안 된다. 다만
대조군 자격과는 무관하다 — 위에서 보듯 no-op 0건이어도 대조군은 된다.

**2차 확대(political·geopolitical)는 이제 지표를 버리지 않아도 된다.** 대조군이
비-파일럿 전체이므로 그 둘을 파일럿으로 옮겨도 7개가 남는다. `test_control_group_is_not_empty`
는 그래도 남겨 둔다 — 13개를 전부 파일럿으로 켜는 날에는 여전히 대조군 비가 소멸하고,
그때는 오염 가드가 공집합이라 통과해 버리기 때문이다. 지표가 조용히 사라지는 경로를
막는 것이 이 가드의 일이다.

같이 추가한 `test_every_mapped_collector_is_either_pilot_or_control` 은 플래그가
되돌아가는 경우를 잡는다. 그 수집기는 파일럿에서 빠지는데 대조군에도 없어 **어느
지표에도 나타나지 않는다** — 커밋이 다시 늘어나도 도구는 조용하다. 상보성으로 단언해
확대할 때마다 테스트를 고칠 필요는 없게 했다.

**표본을 합치는 것 — `--collector all`.** 확대만으로는 해상도가 오르지 않는다.
스크립트가 전 구간 단일 `args.collector` 기준이라 `--collector regulatory` 한 축만
측정하기 때문이다. 그래서 묶음 집계를 같이 넣었다.

핵심은 **층화**다. 수집기마다 파일럿 시작이 다르므로(regulatory 08-10, 확대분은 그
뒤) 하나의 경계로 전부 자르면 반드시 틀린다 — 이른 경계를 쓰면 아직 파일럿이 아니던
확대분 구간이 '후' 로 들어가고, 늦은 경계를 쓰면 regulatory 관측일이 통째로 버려진다.
각 수집기를 자기 경계로 가른 뒤 더한다. 경계는 상수 표가 아니라 `git log -S` 로
워크플로우에서 도출한다.

합산하는 것과 하지 않는 것:

| 절 | 합산 | 이유 |
|---|---|---|
| [1] 커밋 수 · [2] skip/실행 · [3] 중복 · [5] 누출·오검출 | ✓ | 사건 수라 그냥 더해진다 |
| [4] 실행당 커밋 | ✓ (층별 경계) | 분자·분모가 같은 수집기 것이라 경계가 섞이지 않는다 |
| [4] 대조군 비 | ✗ 수집기별 | 합산하면 대조군 커밋을 파일럿 수집기 수만큼 중복 계상한다 |

**합산의 성격 — combined ratio이지 층화 추정량이 아니다** (2026-08-12 리뷰). 실행당
커밋은 층별 비를 합치는 게 아니라 분자·분모를 먼저 더한다. 전·후 풀의 층 구성이 다르면
**층 내 효과가 전부 정확히 0이어도 합산 값은 0이 아니다**(Simpson). 파일럿 시작이
어긋나 있으면 구성은 반드시 다르므로 이 조건은 항상 성립한다. 리뷰어가 만든 수치 예:
파일럿 효과 0, 수집기별 기저 커밋/실행만 실측 범위(0.86~1.00)로 다르게 두면 합산
델타가 +2.2% 로 나오고, regulatory 기저를 0.80 으로 낮추면 -5.9% 라는 가짜 절감이 된다.

그래서 **층별 값을 함께 출력**한다. 합산과 층별이 갈리면 그 자리에서 보인다. 제대로 된
요약이 필요하면 층별 델타의 역분산 가중이나 Poisson 회귀
(`commits ~ offset(log runs) + collector + post_pilot`)가 맞고, 대조군 비의 중복 계상도
Mantel-Haenszel 로는 풀린다 — 다만 현 표본은 층당 4~5건이라 어느 쪽도 안정적이지 않아
미뤘다. (문서 초안은 "합산할 방법이 없다" 로 단정했는데 그건 사실이 아니다.)

**절감 숫자에는 신뢰구간을 붙인다.** 초안은 `[2]` 의 skip 비율에만 Wilson 을 붙이고
`[4]` 는 점추정만 냈는데, 그러면 숫자가 실제보다 정밀해 보인다. `LoadRatio.delta_ci_pct()`
가 Katz 표준오차 `sqrt(1/a+1/b+1/c+1/d)` 로 로그 축 대칭 구간을 낸다. 현 표본에서는
**두 지표 모두 구간이 0을 포함한다** — 방향조차 식별되지 않으므로 출력에 그렇게 적는다.

```
실행당 커밋   전 1.00 (14/14)  후 0.71 (5/7)   → -28.6%  95%CI [-82%, +180%]  ※ 0 포함 — 방향 미식별
대조군 비     전 0.200 (14/70) 후 0.156 (5/32) → -21.9%  95%CI [-74%, +136%]  ※ 0 포함 — 방향 미식별
```

이것이 게이트를 절감 %가 아니라 포착률(누출·오검출·중복)로 읽는 결정을 **강화한다.**
절감 %로 게이트를 걸었다면 현 표본으로는 어떤 결론도 낼 수 없다.

게이트 경과일은 **가장 늦게 시작한** 수집기 기준이다. 가장 이른 것으로 재면 확대분이
아직 하루도 안 돌았는데 "3일 충족" 이 된다.

**독립 구현 리뷰에서 나온 결함 두 개 (2026-08-12)** — 둘 다 조용히 거짓 판정을 만든다:

- **`-S` pickaxe 는 값 전환을 못 본다.** 경계 도출이 `-S "skip-noop-state-commits"`
  였는데, `-S` 는 문자열 **출현 횟수**가 변한 커밋만 잡으므로 키를 그대로 두고 값만
  `'false'` → `'true'` 로 뒤집은 커밋을 놓친다. 임시 레포 실측에서 08-05(`'false'`
  도입)를 돌려줬고 정답은 08-25(`'true'` 전환)였다 — **20일 이른 경계**. 그 사이의
  정상 no-op 커밋이 전부 누출로 잡힌다. 대조군 워크플로우에 "여긴 꺼져 있음" 을
  명시하려고 `'false'` 를 적어 두는 것은 현재 가드를 전부 통과하므로(대조군이니
  orphan 도 오염도 아니다) 이 경로는 가설이 아니라 열려 있었다. `-E -G <값 인식 ERE>`
  로 바꿨다. `-E` 를 명시하는 이유는 기본 문법(BRE)에서 `?` 가 리터럴이라 인용부호
  옵셔널이 깨지고, 사용자 git 설정에 좌우되면 조용히 달라지기 때문이다.
- **모르는 수집기 이름이 모든 게이트를 통과시킨다.** `--collector regulatoy` 오타 하나면
  커밋 0건 · 중복 0건 · 누출 0건 · 포착률 PASS · **exit 0** 이 나온다. 한 건도 검사하지
  않은 실행이 파일럿이 완벽히 동작했다는 증거로 보고된다. `all` 경로만 fail closed 였고
  단일 경로에는 이름 검증이 없었다. 이제 `COLLECTOR_WORKFLOWS` 에 없으면 거부한다(rc 2).

**`--collector all` 을 실제로 돌려 보고 나온 결함 두 개** — 단위 테스트로는 둘 다 보이지 않았다:

- **폴백 경계가 거짓 FAIL 을 만들었다.** 확대분이 아직 `main` 에 없는 상태에서
  regulatory 의 경계를 물려주자, 그 수집기들이 정상적으로 만든 no-op 커밋 17건이
  전부 "누출" 로 보고됐다. 파일럿이 켜지지도 않았는데 skip 이 동작하지 않았다고 말한
  것이다. 경계를 모르면 **그 수집기를 집계에서 뺀다** — 없는 데이터보다 틀린 데이터가
  나쁘고, 누출 0건은 게이트라서 거짓 FAIL 이 특히 비싸다.
- **중복 게이트에 시간 범위가 없었다.** 첫 실행이 crypto 의 2026-03-11 · 03-13 포스트
  쌍을 FAIL 로 보고했다 — 파일럿보다 5개월 앞선다. 게이트가 묻는 것은 "파일럿이 중복을
  만들었는가" 이므로 관측 창으로 한정했다. 단, 묶음 전체를 자르지는 않는다. 재발행은

#### 여기서 나온 결함 — `[2]` 의 분모가 파일럿 후로 한정되지 않는다

`collect_skip_counts` 는 `gh run list --limit N` 의 최근 N 실행을 그대로 세는데,
파일럿 경계로 자르지 않는다. 이번 실행에서 조사한 20건 중 **8건이 파일럿 전**
(08-07 22:34 ~ 08-10 07:46)이고, 그 실행들은 코드가 없어 **구조적으로 skip 할 수
없다.** 분모에 들어갈 수 없는 표본이 들어가 비율이 희석된다:

| | skip/실행 | 비율 | 95% CI |
|---|---|---|---|
| 출력값 (전·후 혼합) | 5/20 | 25.0% | [11.2%, 46.9%] |
| **파일럿 후만** | 5/12 | **41.7%** | [19.3%, 68.0%] |

방향이 나쁜 쪽이다. 파일럿 전 regulatory 의 실측 no-op 비율은 55.2%(위 "1차 확대"
표)인데, 희석된 25.0% 의 **CI 상한 46.9% 는 그 값을 배제한다** — "skip 이 기대보다
덜 걸린다" 는 잘못된 인상을 준다. 후만 보면 41.7% CI [19.3%, 68.0%] 로 55.2% 를
정상적으로 포함한다.

게이트 판정은 바뀌지 않는다 — 판정은 `[3]`·`[5]` 가 하고 둘 다 사건 유무라 분모와
무관하다. `[2]` 는 "새 코드 경로가 실행되기는 했는가"(표본 0이면 판정 불가)를 보는
지표이고 5 > 0 은 그대로다. 그래도 출력에 실린 비율이 틀렸다.

**고쳤다 (2026-08-14).** `collect_skip_counts` 가 `pilot_start` 를 받아
`filter_runs_after` 로 `createdAt` 이 경계 **뒤인** 실행만 센다. 경계는 배타적이다 —
머지 시각과 같은 시각에 시작한 실행은 새 코드로 돌았다는 보장이 없다. 경계를 층별로
넘기므로 `--collector all` 에서도 수집기마다 자기 경계로 잘린다. `createdAt` 을 못
읽는 실행은 남기지 않고 **버린다**(경계를 모르는 표본을 분모에 넣으면 같은 희석이
재발한다). 재실행 결과가 표의 아랫줄과 일치한다:

```
합계  실행 12건 중 skip 5건
skip 비율 41.7% — 95% CI [19.3%, 68.0%] 폭 0.49
```

부수 효과 하나: `--run-limit` 은 이제 gh 에서 **가져올** 실행 수이고 필터 뒤 표본은
그보다 작다. 가져온 것이 전부 파일럿 후면 표본이 상한에 묶였을 수 있으므로 그때는
`--run-limit` 을 올리라고 안내한다 — 표본이 조용히 잘리는 것을 막는다.
